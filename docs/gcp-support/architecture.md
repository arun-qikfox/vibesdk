# GCP App Engine Deployment Architecture

This document describes the reference architecture for Google App Engine deployment in VibeSDK.

## 🏗️ High-Level Architecture

```
┌─────────────────────────────────────────────────────────────┐
│                    VibeSDK Platform                         │
│                  (Cloudflare Worker)                        │
└─────────────────────────────────────────────────────────────┘
                            │
                            │ User requests deployment
                            ▼
┌─────────────────────────────────────────────────────────────┐
│         Deployment Target Selection                         │
│  (deployment-config.ts)                                    │
│  - Checks DEFAULT_DEPLOYMENT_TARGET env var                 │
│  - Default: 'app_engine'                                    │
└─────────────────────────────────────────────────────────────┘
                            │
                ┌───────────┴───────────┐
                │                       │
                ▼                       ▼
    ┌──────────────────┐    ┌──────────────────┐
    │  Cloudflare      │    │  GCP App Engine   │
    │  Deployment      │    │  Deployment      │
    └──────────────────┘    └──────────────────┘
```

## 🔄 GCP Deployment Flow (Phase 1: Static Frontend)

### Step-by-Step Process

```
1. User Initiates Deployment
   │
   ├─> Agent receives deployment request
   │   Location: worker/agents/core/simpleGeneratorAgent.ts
   │   Method: deployToAppEngine()
   │
2. Get Deployment Configuration
   │
   ├─> Read deployment config
   │   Location: worker/config/deployment-config.ts
   │   Function: getDeploymentConfig(env)
   │   Returns: { target: 'app_engine', isStaticFrontend: true }
   │
3. Execute Deployment
   │
   ├─> Call sandbox SDK client
   │   Location: worker/services/sandbox/sandboxSdkClient.ts
   │   Method: deployToAppEngine(instanceId)
   │
   ├─> Step 3.1: Build Frontend
   │   Command: npm run build
   │   Output: dist/client/ directory
   │
   ├─> Step 3.2: Generate Service Name
   │   Utility: generateShortServiceName(projectName)
   │   Location: worker/services/deployer/appengine-yaml-generator.ts
   │   Format: "prefix-hash" (e.g., "app-a1b2c3d4")
   │
   ├─> Step 3.3: Generate app.yaml
   │   Utility: generateStaticAppYaml(shortServiceName)
   │   Location: worker/services/deployer/appengine-yaml-generator.ts
   │   Output: YAML configuration for App Engine
   │
   ├─> Step 3.4: Create .gcloudignore
   │   Purpose: Deploy only dist/client/ and app.yaml
   │   Excludes: src/, node_modules/, source files, etc.
   │
   ├─> Step 3.5: Authenticate gcloud
   │   Command: gcloud auth activate-service-account
   │   Credentials: GOOGLE_SERVICE_ACCOUNT_KEY (base64-encoded JSON)
   │
   ├─> Step 3.6: Deploy to App Engine
   │   Command: gcloud app deploy app.yaml --quiet
   │   Project: GOOGLE_CLOUD_PROJECT_ID
   │
   └─> Step 3.7: Return Deployment URL
       Format: https://{shortServiceName}-dot-{projectId}.appspot.com
```

## 📁 File Structure and Responsibilities

### Core Files

| File | Purpose | Key Functions |
|------|---------|---------------|
| `worker/config/deployment-config.ts` | Deployment target selection | `getDeploymentConfig()` |
| `worker/services/deployer/appengine-yaml-generator.ts` | Shared YAML/service name generation | `generateStaticAppYaml()`, `generateShortServiceName()` |
| `worker/services/sandbox/sandboxSdkClient.ts` | Actual deployment execution | `deployToAppEngine()` |
| `worker/services/deployer/appengine-deployer.ts` | Placeholder/interface (future use) | `deployStaticFrontend()` |
| `worker/agents/core/simpleGeneratorAgent.ts` | Agent integration | `deployToAppEngine()` |

### Configuration Files Generated

| File | Generated By | Purpose |
|------|--------------|---------|
| `app.yaml` | `generateStaticAppYaml()` | App Engine configuration |
| `.gcloudignore` | `sandboxSdkClient.ts` | File exclusion for deployment |

## 📦 Deployment Package Structure

### What Gets Deployed

```
Deployment Package:
├── app.yaml                    # App Engine configuration
└── dist/
    └── client/                 # Frontend build output
        ├── index.html
        ├── assets/
        │   ├── *.js
        │   ├── *.css
        │   └── *.png, *.svg, etc.
        └── ...
```

### What Gets Excluded (.gcloudignore)

```
Excluded:
├── src/                        # Source code
├── node_modules/              # Dependencies
├── .git/                      # Version control
├── *.ts, *.tsx, *.jsx        # Source files
├── package.json               # Build config
├── vite.config.ts             # Build config
├── .gcloud-key.json          # Temporary auth file
└── ... (everything except dist/client/ and app.yaml)
```

## 🌐 URL Structure

### App Engine Service URLs

- **Format**: `https://{service-name}-dot-{project-id}.appspot.com`
- **Service Name**: Generated via `generateShortServiceName()` (e.g., `app-a1b2c3d4`)
- **Project ID**: From `GOOGLE_CLOUD_PROJECT_ID` environment variable
- **Example**: `https://app-a1b2c3d4-dot-my-project-123456.appspot.com`

### Why `-dot-` Format?

App Engine uses `-dot-` to separate service name from project ID in URLs when using custom service names. This is the standard format for App Engine service URLs.

```

   │

   │

```

## 🔍 Key Design Decisions

### 1. Why Separate YAML Generator?
- **Single Source of Truth**: One place to maintain app.yaml format
- **Reusability**: Can be used by multiple deployment paths
- **Testability**: Easier to test YAML generation independently
- **Consistency**: Ensures same configuration across all deployments

### 2. Why Short Service Names?
- **Domain Limits**: App Engine has URL length limitations
- **Uniqueness**: Hash-based suffix ensures uniqueness
- **Readability**: Prefix from project name maintains readability
- **Compatibility**: Works with App Engine naming constraints

### 3. Why .gcloudignore?
- **Size**: Reduces deployment package size significantly
- **Security**: Prevents uploading sensitive files (source code, keys)
- **Speed**: Faster uploads with smaller packages
- **Best Practice**: Standard approach for App Engine deployments

### 4. Why dist/client/?
- **Build Tool Output**: Vite/React builds output to dist/client/
- **Separation**: Keeps client and server builds separate
- **Flexibility**: Allows future backend deployment to dist/server/

## 📊 Comparison: Cloudflare vs GCP

| Aspect | Cloudflare Workers | GCP App Engine |
|--------|-------------------|----------------|
| **Frontend** | Workers for Platforms | Static files (dist/client/) |
| **Backend** | Workers (serverless) | App Engine (Flexible/Standard) |
| **Data Store** | D1 (SQLite) / KV | Firestore (default) or HTTP provider |
| **Storage** | R2, KV | Cloud Storage, Firestore |
| **Deployment** | Wrangler CLI | gcloud CLI |
| **Config File** | wrangler.jsonc | app.yaml |
| **URL Format** | *.workers.dev | *.appspot.com |
